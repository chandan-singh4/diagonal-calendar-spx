# 1. Executive Summary

## 1.1 What this project currently does

A locally-hosted, single-user options analytics platform for SPX diagonal calendar spreads. It runs as two independent processes on a Windows machine:

- **`collector.py`** — a headless daemon that polls the Charles Schwab Market Data API during US market hours (60s at open/close, 300s midday), fetches the SPX option chain across the nearest 20 expirations within ±300 points of spot, and writes immutable snapshots to SQLite. It has never been read by the dashboard and never reads UI state.
- **`app.py` + `pages/journal.py`** — a Streamlit dashboard that is a pure reader of that database. Six tabs plus a trade journal, surfacing IV term structure, per-strike IV history, a cross-sectional "Mission Control" opportunity scanner, an entry-lock position monitor, and full trade lifecycle CRUD with P&L accounting.

## 1.2 The problem it solves

Retail brokerage platforms show the current option chain but do not persist it. This project's core insight is that the decision-relevant signal for this strategy is **temporal and cross-sectional**, not point-in-time:

1. *Is now a reasonable time to enter a diagonal calendar?* — requires IV term-structure history at the specific strikes you would trade, not just ATM, not just today.
2. *Has an open position reached the point where it can be transformed into a risk-reduced Iron Condor?* — requires the "Transform Difference" (short-leg premium minus protective-wing cost) tracked continuously against a threshold.

No commercial product the trader has access to answers either question. Building the historical store *is* the product; the dashboard is a view over it.

## 1.4 Strengths — and these are real

1. **The writer/reader architecture is correct and rigorously enforced.** `collector.py` is the sole writer; `app.py` never writes market data. WAL mode plus `PRAGMA query_only = ON` on the read path (`db.py:169-189`) means the dashboard *physically cannot* take a write lock. This is a better isolation guarantee than most production systems bother with.

2. **`collector.py` is genuinely production-grade.** Snapshots are created `PARTIAL` before the chain fetch and finalized `COMPLETE`/`FAILED` after, so a crash leaves an auditable record rather than silent loss. Gap detection distinguishes `HOLIDAY` / `MARKET_CLOSED` / `COLLECTOR_OFFLINE`. Auth errors are pattern-matched to force re-authentication. Sleep is drift-corrected against `time.monotonic()`. This module needs almost nothing.

3. **`iv_engine.py` is a clean analytics core.** Pure functions, no I/O, no `st.*`, dataclass return types, explicit `None` handling on missing legs. This is the one module that is already unit-testable today.

4. **Intellectual honesty about unvalidated claims is exceptional and rare.** The 2026-06-25 audit retracted the project's own central thesis (that IV ratio < 1.0 is "favorable") on the grounds that it rested on a single paper trade, corrected the backwardation/contango terminology, and demoted the claim to `HYPOTHESIS` rather than flipping it to the opposite rule. Metrics carry `HYPOTHESIS` labels in the UI. Colors were deliberately de-valenced so the interface would not imply an edge that hasn't been demonstrated. **Do not lose this during any refactor. It is the most valuable asset in the repository and it is not in the code.**

5. **`DEV_JOURNAL.md` has real forensic value.** The 2026-07-07 entry documenting the Plotly rangebreak corruption — including the falsification sequence and the Windows venv double-process lesson — is the kind of institutional memory most teams never write down.

## 1.5 Weaknesses

1. **The database is on an unmanaged 20 GB/year trajectory.** Measured: 1.81 GB, 7.82 M `option_rows`, 2,608 snapshots, over 31 calendar days (2026-06-23 → 2026-07-24). That is ~82 MB per trading day. There is no retention policy, no archival, no partitioning, and no cleanup. See §5.1.

2. **`app.py` is a 4,230-line procedural script, not a module.** 257 top-level statements. Tabs are `if st.session_state["active_tab"] == "..."` blocks operating on shared module-level `_`-prefixed variables. Lines 72–829 are a 757-line embedded CSS string. Business logic, SQL orchestration, chart construction, and raw HTML are interleaved throughout. See §3.2.

3. **Zero automated tests.** Not "thin coverage" — none at all. The 2026-07-07 journal entry describes a multi-day debugging session (ghost lines, wrong chronology, dead tooltips) resolved only by manual binary-search toggling in a live browser. A rendering-contract test would not have caught the Plotly bug, but tests around `resolved_pl`, `ic_expiry_pnl_per_share`, `transform_diff`, and the strike-resolution logic would make every future change cheaper and safer.

4. **`DOCUMENTATION.md` claims canonical authority it no longer has.** It declares "In any conflict between this document, dashboard labels, source code, and DEV_JOURNAL.md, this document governs." But it documents `transform_credit()` and `calendar_edge()` as core metrics — **neither function is called anywhere in the application**. It stops at v4.1; the code is at v4.2. **Entry Locks**, a substantial shipped feature (30 references in `app.py`, its own persistence file, its own chart mode), appears in it exactly once, incidentally. A source of truth that is wrong is worse than no source of truth, because it is trusted.

5. **`README.md` is entirely obsolete.** It describes an "MVP scaffold" at Phase 2, instructs `cp .env.example .env` (**that file does not exist**), and tells the user to "toggle Demo Mode off in the sidebar" — Demo Mode was removed from the UI and `demo_data.py` is now fully orphaned. This is the first file any reader opens.

6. **Repository hygiene is broken, including a corrupted `.gitignore`.** `.gitignore` has UTF-16LE bytes appended to a UTF-8 file (a PowerShell `Out-File`/`Add-Content` encoding accident) — the final entry reads `p\0i\0n\0n\0e\0d\0...` and does not match anything. Consequently `pinned_pairs.json`, `chart_colors.json`, `eligible_history.json`, `entry_locks.json`, and a 486 KB actively-appended `collector.log` are all tracked in git. See §2.4.

7. **The single most important business constant is duplicated four times as a literal.** The $5.00 transform threshold appears at `app.py:1575`, `app.py:3103`, `app.py:3686`, and as a hardcoded string at `app.py:3704`. It is not in `config.py`. `DOCUMENTATION.md` §9.1 states this value must be recalibrated to $6.50–$7.00 from live fills — that recalibration is currently a multi-file grep with a real chance of missing an instance.

# 3. Architecture Review

## 3.1 Separation of concerns — split verdict

**The data tier: excellent.** The writer/reader boundary is not just documented, it is *enforced at the SQLite connection level*. `_make_conn(read_only=True)` sets `PRAGMA query_only = ON`, making a dashboard write physically impossible rather than merely discouraged. The `PARTIAL → COMPLETE/FAILED` snapshot state machine means a crashed cycle leaves an auditable record. `db.py` is the only module issuing SQL, and that rule holds across all callers. This tier would survive a code review at most companies.

**The presentation tier: none.** Within `app.py` there is no separation whatsoever between:

- HTML/CSS (757-line style block + 51 `unsafe_allow_html=True` sites)
- Layout (`st.columns`, tab dispatch)
- State management (79 `session_state` references)
- Cache orchestration (14 decorated loaders)
- Business logic (scanner, Mission Control ranking, eligibility registry, entry locks)
- Data access orchestration
- Chart construction (5 substantial Plotly builders inline)
- Formatting/presentation helpers

A representative example — `app.py:3103-3135` computes the transform-difference business rule, decides the visual state, renders a Unicode progress bar, and emits inline-styled HTML, in one contiguous block, with `_THRESHOLD = 5.0` declared locally.

## 3.2 Modularity: 2/5

`app.py` defines 30 functions across 4,230 lines. The other **257 top-level statements** execute in file order on every rerun. Tabs are not components — they are `if` blocks reading shared module-scope variables (`_diag_mark`, `_ic_mark`, `_straddle`, `_theta_diff`, `_iv_pct`, `_liquidity`) computed hundreds of lines earlier. This creates implicit temporal coupling: moving a block changes behavior, and there is no signature anywhere that declares what a tab needs.

## 3.3 Maintainability: 2/5

The single strongest maintainability signal in the repo is a negative one: **the 2026-07-07 journal entry documents a multi-day debugging session** that required manually toggling Plotly config in a live browser and writing six throwaway diagnostic scripts, because there was no faster way to isolate the fault. That is what a codebase with no tests and no seams costs, measured in days.

The countervailing signal is that `DEV_JOURNAL.md` captures the lesson so precisely that the same bug will not recur. Documentation is currently substituting for structure — which works until the volume of things to remember exceeds what one person can hold.

## 3.4 Scalability: 2/5

- **Data volume — the binding constraint.** 82 MB/trading day → ~20 GB/year, unmanaged. SQLite handles this size, but backups, VACUUM, and any future full-table migration become progressively more painful. Query latency is *currently fine* (measured below) — this is a storage and operations problem, not yet a performance one.
- **Concurrency — fine and unlikely to change.** Single writer, single reader, WAL. Correct for the actual requirement.
- **Compute — well handled.** Mission Control's two-phase design (in-memory sweep across 21 offsets × all expiry pairs; history queries only for the small candidate set, capped at 20/tier) is a genuinely good scaling decision, and the reasoning is documented at `app.py:1559-1586`.

## 3.5 Extensibility: 2/5

Adding a metric today requires touching: `iv_engine.py` (compute), `app.py` (load, cache, place in a tab, style, write help text), and `DOCUMENTATION.md` (define, register as HYPOTHESIS). There is no metric registry, no component contract, no plugin seam. The chart-color system (`DEFAULT_CHART_COLORS` → auto-generated pickers) is the one place a proper extension point exists — and it demonstrates the author knows how to build them.

## 3.6 Testability: 1/5

| Module | Testable today? |
|---|---|
| `iv_engine.py` | **Yes** — pure functions, no I/O. Could reach high coverage in a day. |
| `db.py` | **Yes** — takes `db_path`; point at a tmpfile fixture. |
| `collector.py` | **Mostly** — `get_session`, `_classify_gap`, `_build_option_rows`, `_compute_atm_iv_records` are pure and take plain inputs. Only `_run_cycle`/`main` need a mock client. |
| `schwab_client.py` | **Partly** — `chain_to_dataframe`, `filter_chain_by_strike_window` are pure. |
| `pages/journal.py` | **Partly** — `resolved_pl`, `ic_expiry_pnl_per_share`, `derive_ic`, `compute_stats`, `_ic_payoff_chart` are pure and are the **highest-value test targets in the repo** (they compute money). |
| `app.py` | **No** — importing it executes the entire dashboard. |

**The important nuance: this codebase is far more testable than it is tested.** Roughly 60% of the logic is already in pure functions with plain-data signatures. The tests don't exist not because the design prevents them, but because nobody wrote them. That makes this the cheapest high-value fix available.

## 3.7 Readability: 3/5

Genuinely strong at the line and function level. Docstrings explain *why*, not *what* — `schwab_client.get_client()` documents why the manual OAuth flow was chosen over `easy_client` and what breaks otherwise; `_compute_transform_scanner` explains the leading-underscore cache-key trick. Naming is consistent and domain-accurate.

Weak at the file level, purely from scale. Finding "where is Transform Difference computed" means searching 4,230 lines and finding four candidate sites.

## 3.8 Recommended target architecture

Not a rewrite. A **decomposition that preserves every line of working logic** and is valuable regardless of what happens to the UI:

```

│   ├── scanner.py           # offset sweep, ranking (lifted verbatim from app.py)
│   ├── pnl.py               # resolved_pl, ic_expiry_pnl, derive_ic (from journal.py)
│   └── models.py            # dataclasses shared across layers
├── data/
│   ├── connection.py        # _make_conn, get_conn, managed_conn
│   ├── schema.py            # DDL + migrations
│   ├── reads.py             # query functions
│   ├── writes.py            # collector + journal writes
│   ├── retention.py         # NEW — archival / pruning (§5.1)

├── collection/
│   ├── daemon.py            # ex-collector.py
│   └── schwab.py            # ex-schwab_client.py
├── ui/                      # thin — presentation only, calls core/

│   ├── components/          # kpi_card, chart_card, note, sparkline…

    └── fixtures/            # canned chain JSON, seeded DB
```

**Why this ordering matters:** everything in `core/` and `data/` is UI-framework-agnostic. If the dashboard is later rebuilt in React/Next.js, `core/` is reused unchanged and only `ui/` is discarded. If Streamlit is kept, the same decomposition makes it testable and navigable. **The decomposition is the decision that doesn't need the frontend decision made first** — which is why I recommend it before, not after, §6.

# 5. Data Pipeline Review

## 5.1 Storage — the primary bottleneck

**Measured, not estimated:**

| Metric | Value |
|---|---:|
| Database size | **1.81 GB** |
| Coverage | 2026-06-23 → 2026-07-24 (31 days, ~22 trading days) |
| Snapshots | 2,608 (2,605 COMPLETE, 3 FAILED) |
| `option_rows` | **7,816,508** |
| Rows per snapshot | ~3,001 (≈19.25 expiries × ~156 contracts) |
| Snapshots/trading day | ~118 |
| **Growth rate** | **~82 MB per trading day** |
| **Projected 12-month size** | **~20 GB** |
| Free pages | 0 (no VACUUM headroom being wasted — growth is genuine) |

**Table/index breakdown (via `dbstat`):**

| Object | Size |
|---|---:|
| `option_rows` (data) | 1,011.6 MB |
| `idx_option_rows_contract_snap` | 244.1 MB |
| `uq_option_rows_contract` | 227.8 MB |
| `idx_option_rows_contract` | **217.6 MB — redundant** |
| `idx_option_rows_snapshot_id` | **100.0 MB — redundant** |
| everything else | < 8 MB combined |

**Indexes are 790 MB — 44% of the database — on one table.**

## 5.2 Two indexes are provably redundant — ~318 MB recoverable

- `idx_option_rows_contract (expiry_date, strike, right)` is a strict **left prefix** of `idx_option_rows_contract_snap (expiry_date, strike, right, snapshot_id)`. Every query the former can serve, the latter serves. → **217.6 MB dead weight.**
- `idx_option_rows_snapshot_id (snapshot_id)` is a strict left prefix of `uq_option_rows_contract (snapshot_id, expiry_date, strike, right)`. → **100.0 MB dead weight.**

Beyond the ~17.6% size reduction, both are maintained on **every one of the ~3,000 inserts per collection cycle**, so dropping them also reduces write cost and lock-hold time against the reader.

*(One caveat to verify before dropping: `dedupe_option_rows.py` deliberately used `idx_option_rows_snapshot_id` for chunked per-snapshot lookups. The composite unique index serves that access pattern equally well as a prefix, but the migration script should be re-checked before the drop rather than assumed.)*

## 5.3 Query performance — currently healthy

Measured against the live 1.81 GB database:

| Query | Rows | Latency |
|---|---:|---:|
| `get_latest_complete_snapshot` | 1 | **4 ms** |
| `get_option_chain` (full snapshot) | 3,096 | **17 ms** |
| `get_atm_iv_history` (20 d) | 1,678 | **11 ms** |
| `get_transform_mark_history` (90 d, 6-leg join) | 1,166 | **65 ms** |
| `get_diagonal_history` (90 d) | 1,285 | **61 ms** |

**Conclusion: query latency is not currently a problem, and I want to be precise about that** — the v4.1 fan-out fix (unique index + `GROUP BY s.snapshot_id`) genuinely worked, and the ~56 ms figure recorded in `DOCUMENTATION.md` §15.6 reproduces today at ~65 ms on a database that has since doubled. The storage trajectory is the issue, not query speed. Storage will, however, eventually *become* a query problem as the working set outgrows OS page cache.

## 5.4 Collection — well engineered

Session detection, drift-corrected sleep, `PARTIAL→COMPLETE/FAILED` state machine, gap classification, `INSERT OR IGNORE` idempotency, non-fatal VIX degradation. **Recommend no changes** beyond the observability additions below.

Three real gaps:
1. **No automated start.** `register_collector_task.ps1` exists but was never registered (confirmed in the 2026-07-07 journal). Collection depends on the user remembering. A missed morning is permanently lost data — this is the highest-consequence operational gap in the system.
2. **No liveness alerting.** If the collector dies mid-session, the dashboard shows a staleness dot; nothing else happens. No email, no notification, no watchdog.
3. **Token expiry is a recurring manual chore.** Schwab's 7-day refresh window means re-auth every week; the dashboard warns at day 6, but the procedure is manual copy-paste.

## 5.5 Data integrity — one real remaining exposure

The v4.1 duplicate/sawtooth fix was correct and is holding (`uq_option_rows_contract` confirmed present; `INSERT OR IGNORE` in place).

**The remaining exposure is that `INSERT OR IGNORE` also silences legitimate write failures.** A constraint violation from a genuine data problem (e.g. a `CHECK` failure on `right`) is discarded identically to a benign duplicate, with no count returned and no log line. Recommend capturing `cursor.rowcount` and logging when `inserted < len(rows)`.

**Sidecar JSON is the weakest link.** `eligible_history.json` (599 KB), `entry_locks.json`, `chart_colors.json` have no schema, no validation, no atomic-write guarantee, and no backup. A partial write during an interrupted save loses the entire non-ATM crossing registry — data that, by design, cannot be reconstructed from the database (that is precisely why the registry exists, per `DOCUMENTATION.md` §14.2.3).

## 5.6 Caching — well designed
Twelve `@st.cache_data` loaders, all keyed on `snapshot_id`, all with `ttl` and `max_entries` after the v4.1 fix. The `_chain_df` leading-underscore trick to skip DataFrame hashing is correct and well documented. **No changes recommended.**

## 5.7 Bottlenecks, ranked

1. **Storage growth** (~20 GB/yr) — no mitigation exists
2. **Redundant indexes** (318 MB, plus per-insert cost)
3. **Collector reliability depends on human memory** — permanent data loss on failure
4. **Sidecar JSON durability** — silent, unrecoverable state loss
5. Query latency — **not currently a bottleneck**

## 5.8 Recommendations

**Immediate (safe, high value):**
- **Back up `data/dashboard.db` before anything else touches it.** One month of irreplaceable data currently exists in exactly one place.
- Drop the two redundant indexes; `VACUUM` (reclaims ~318 MB).
- Drop the three orphaned legacy tables.
- Register the collector scheduled task; add a liveness check.
- Add log rotation (`RotatingFileHandler`) and untrack `collector.log`.

**Short term:**
- **Define a retention policy.** The design question to settle: full per-strike history is only genuinely needed for expiries you actually traded or studied. Options, roughly in increasing complexity: (a) prune `option_rows` for expiries more than N days past expiration, keeping `atm_iv_by_expiry` forever (it is only 3.7 MB for the full month — ~0.2% of the DB, and it powers most of the historical charts); (b) archive aged data to a separate `history.db` attached read-only on demand; (c) downsample old intraday snapshots to hourly beyond N days. **Option (a) alone would likely cut steady-state size by an order of magnitude.** This needs your input — see the questions at the end.
- Atomic writes (`tmp` + `os.replace`) and schema validation for sidecar JSON.
- Surface `collection_gaps` in the dashboard — the data is collected and never shown.

**Medium term:**
- Consider a narrower hot table (`snapshot_id, expiry, strike, right, mark, iv` only) for chart queries, with full rows retained separately.
- Automated nightly backup with rotation.

**Structural recommendation:** `DOCUMENTATION.md` at 1,659 lines is doing five jobs (strategy reference, math reference, dashboard manual, data architecture, per-version changelog). Split it into `docs/STRATEGY.md`, `docs/METRICS.md`, `docs/DASHBOARD.md`, `docs/DATABASE.md`, and `CHANGELOG.md`. Each then has one owner and one reason to change — which is the actual mechanism that stops drift. Its current structure *causes* the drift: appending a new `§N` per release means older sections are never revisited.

## Dependency graph

```
M0 Cleanup ──► M1 Tests ──► M2 Refactor ──┬──► M3 Data Hardening ──► M8 Deployment

                                          ├──► M4 API ──► M5 Dashboard (gated at 5.0)

                                          └──► M6 Analytics ──► M7 ML (gated on trade count)
```

**Critical path: M0 → M1 → M2.** Nothing else is safe until those three are done.

**Sequencing rationale — the one thing I'd push back on hardest:** it is tempting to start with M5 (the dashboard is what you look at every day, and the frontend question is the interesting one). **Doing M5 before M1/M2 would be a serious mistake.** It would rebuild a UI on top of untested, undecomposed logic, with no mechanism to verify the new UI computes the same numbers as the old one — in a tool whose outputs drive real money. M0–M2 are unglamorous. They are also the entire difference between "a prototype that works" and "a professionally maintained production repository," which is the stated goal.
